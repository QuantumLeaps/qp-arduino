# RP2040 Blinky on the qualification fixture — 2026-09-30

First target run of qp-arduino (QP/C++ v7.3.4, QV kernel) on the recorded
RP2040 fixture. Everything here was produced by the automated procedure below
from branch `upgrade/qpcpp-v7`; the exact tree is named per capture in
"Firmware under test". Interpretation lives in `UPGRADE_QPCPP_V7.md`
("RP2040 Target Results — 2026-09-30"); this directory holds the raw evidence.

## Fixture

- `mouse-joystick-pcb` rev 0, unit E4654C159F2C2534, 36 V input unplugged,
  powered and programmed over USB. Enumerates as `Orb Weaver qp-arduino-rp2040`
  (`2e8a:f00a`) with the flash unique ID as serial.
- InstrumentPort-40 `J1501` → 40-pin FFC → `la5032-instrument-port-adapter`
  v1.0 → Kingst LA5032 (`77a1:01a2`, `kingst-la2016` driver, `conn=1.53`).
- Channel map: LA5032 CH16 = `TRIG0` = `FW_TRIG0` = GP25 = the Blinky LED
  (toggles every 50 ticks); CH17 = `TRIG1` = `FW_TRIG1` = GP21 = tick-ISR probe
  (high for the duration of the 100 Hz tick callback).

## Host tools

- Flashing: `pixi run upload-blinky-bsp-rp2040 /dev/ttyACM0` (PlatformIO
  6.2.0 from Pixi, `picotool` after the 1200 baud touch; `upload.log`).
- Trace: `qspy` 7.3.3 built from QTools tag v7.3.4 by
  `tools/quantum_leaps_tools.py`, run as
  `qspy -k -c /dev/ttyACM0 -b 115200 -o -r c0`.
- Analyzer: `sigrok-cli` 0.7.2 / libsigrok 0.6.0 from `instrument-control`'s
  Guix manifest (`guix shell -m manifest.scm -- sigrok-cli ...`), captures
  exported with `-O vcd`, analyzed by `analysis/analyze_blinky_capture.py`.

## Firmware under test

All images come from branch `upgrade/qpcpp-v7` at merge commit `55ee412` plus
the example changes committed with this directory. See `firmware-hashes.txt`.

- **A** `rp2040_mouse_joystick`, `-DQS_ON`, universal single-lane boot2. Flashed
  twice: first without, then with the 5 s QS host wait (`upload.log` is the
  second upload). Used for captures A1 to A3 and the QSPY logs.
- **B** the same environment after the QS write-path fix. Final state of the

- **D** `rp2040_mouse_joystick_fastflash`: A plus the quad-lane

Notes:

- The 600 s capture ran at 100 kSa/s, which under-samples the 1.7 µs tick
  pulse; only its LED column is valid evidence (1,199 consecutive 50-tick
  intervals, largest deviation 0.26 ms, so no tick was missed or doubled).
- "ISR width posting tick" is the tick callback that expires the time event and
  posts it. It costs 35 µs without a trace host or without QS, 65 to 92 µs with
  QSPY attached, and the quad-lane loader does not change it, so XIP cache
  misses are ruled out. Root cause is an open item.
- Tick→LED latency spans the ISR, the QV loop's return from the idle callback
  and the dispatch; with QSPY attached the idle loop's USB CDC writes add
  100 to 300 µs.
- The 11-minute QSPY log has one `<COMMS>` checksum error and sequence gap at
  its start: that is the 52.5 s between QSPY sessions, when stale output
  flushed after the new attach. During the session itself 1,319 intervals
  were continuous (mean 500,000.01 µs, stdev 8.5 µs, no assertions).

## Trace logs

- `qspy/qspy-late-attach-no-dictionaries-15s.txt`: first attach, 25 s after
  boot; shows that USB CDC discards output written before a host opens the
  port (no dictionaries, objects by address).
- `qspy/qspy-attach-after-flash-20s.txt`: after adding the host wait, QSPY
  attached 1.3 s after re-enumeration and received the dictionaries and the
  initial transition.
- `qspy/qspy-10min.txt`: the trace during the 600 s capture (attached late,
  so objects appear by address; addresses resolve via the ELF).
- `qspy/qspy-fastflash-25s.txt`, `qspy/qspy-final-build-15s.txt`: sanity
  sessions for images D and B.
- `captures/sigrok-session-*.log`: the sigrok-cli invocations and results.
