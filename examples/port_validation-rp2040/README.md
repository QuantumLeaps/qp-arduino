# Port validation on the RP2040 fixture

Load generator and probe firmware for qualifying the qp-arduino QV port on
RP2040 (Earle Philhower arduino-pico core, QP/C++ v7.3.4), driven from the
host over QS-RX. Written for the `mouse-joystick-pcb` rev 0 fixture; builds for
any RP2040 board without the fixture flag.

**Keep the fixture's 36 V input unplugged.** The BSP applies the board's safe
state first and never enables the 36 V switch or the GPIO isolation bus.

## Features exercised

- time events every tick (100 Hz), publish/subscribe, direct posting,
  dynamic events from a pool with sequence checking, active-object dispatch,
  the QV idle callback, assertions (`Q_ERROR` on request), QS-TX and QS-RX
- two analyzer probes, the fixture's only free pins:
  GP21 (`FW_TRIG1`, LA5032 ch 17) is high during the tick callback;
  GP25 (`FW_TRIG0`, LA5032 ch 16) takes one of four roles chosen at run time
  by QS command 5: 0 marker pulses, 1 dispatch (default), 2 idle, 3 event
  receipt

## QS commands

| Command | Effect |
|---|---|
| 1 | publish `VALIDATE_SIG` from the command source |
| 2 | post a pool-allocated `DYN_SIG` with `seq = param1` |
| 3 | pulse the marker (role 0) |
| 4 | `Q_ERROR_ID(400)`: `=ASSERT=` record, GP25 high for 2 s, watchdog reset |
| 5 | select the GP25 role (`param1` 0 to 3), echoed as `PROBE_ROLE` |
| 6 | emit `VALIDATION_STAT` (ticks, events, dynamic events) |
| 7 | reset the counters |

## Code organization

```
port_validation-rp2040/
  port_validation-rp2040.ino   setup(): pub/sub, pool, start the Validator; loop(): QF::run()
  validation.hpp               signals, records, event type, Validator interface
  validator.cpp                the Validator active object
  bsp.hpp / bsp.cpp            fixture safe state, probes and roles, tick timer,

```

## Building and running

```sh
pixi run build-port-validation-rp2040
pixi run upload-port-validation-rp2040 /dev/ttyACM0
pixi run validate-rp2040 /dev/ttyACM0        # host-driven procedures, results JSON
```

The host procedure is `tools/port_validation_rp2040.py`; `tools/port_validation_stress.py --port /dev/serial/by-id/...` cycles a fast or deliberately slow trace host against the firmware for an hour and flags any cycle whose tick counter stops advancing. It starts `qspy`,
attaches to its UDP front-end, checks QS-RX (`Trg-Info`), counter progress,
publish, dynamic events, role switching, counter reset and, last, the
assertion path including the reboot and re-attach. Analyzer measurements of
tick period, ISR duration and tick-to-dispatch latency use the same captures
and `analysis/analyze_blinky_capture.py` as the Blinky evidence, with GP25 in
role 1.

Handwritten; not generated by QM.

## Tick source and transport service

The BSP drives the 100 Hz tick from a hardware timer alarm it claims itself
(`hardware_alarm_claim_unused`) and re-arms from its own interrupt, catching
up if a target was missed; the idle loop watches the tick and emits a
`TICK_LOST` user record if it ever has to re-arm it. This replaced a pico-sdk
repeating timer in the core's shared alarm pool, which stopped silently under
trace-host attach/detach cycling. The trace transport is serviced only when
`QP_ARDUINO_QS_SERVICE_BYTES` are pending or `QP_ARDUINO_QS_SERVICE_US` have
passed.
