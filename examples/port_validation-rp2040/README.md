# port_validation-rp2040

Load generator and probe firmware for checking the qp-arduino QV port on an
RP2040 board (Earle Philhower arduino-pico core, QP/C++ v7.3.4), driven from
the host over QS-RX. The Raspberry Pi Pico is the reference board; any board
of that core works. This is how the port was qualified; it is also a template
for checking the port on a new board or core version.

## Features Exercised

- time events every tick (100 Hz), publish/subscribe, direct posting, dynamic
  events from a pool with sequence checking, active-object dispatch, the QV
  idle callback, assertions (`Q_ERROR` on request), QS-TX and QS-RX
- two analyzer probes: `QP_ARDUINO_TICK_PROBE_PIN`, if defined, is high during
  the tick callback; the LED pin (`LED_BUILTIN`, GP25 on a Pico, or
  `QP_ARDUINO_LED_PIN`) takes one of four roles chosen at run time by QS
  command 5: 0 marker pulses, 1 dispatch (default), 2 idle, 3 event receipt

## QS Commands

| Command | Effect |
|---|---|
| 1 | publish `VALIDATE_SIG` from the command source |
| 2 | post a pool-allocated `DYN_SIG` with `seq = param1` |
| 3 | pulse the marker (role 0) |
| 4 | `Q_ERROR_ID(400)`: `=ASSERT=` record, LED pin high for 2 s, watchdog reset |
| 5 | select the LED pin's role (`param1` 0 to 3), echoed as `PROBE_ROLE` |
| 6 | emit `VALIDATION_STAT` (ticks, events, dynamic events) |
| 7 | reset the counters |

## Code Organization

```
port_validation-rp2040/
  port_validation-rp2040.ino   setup(): pub/sub, pool, start the Validator; loop(): QF::run()
  validation.hpp               signals, records, event type, Validator interface
  validator.cpp                the Validator active object
  bsp.hpp / bsp.cpp            probes and roles, tick timer, QS transport and
                               commands, Q_onError, QF/QV callbacks
```

Handwritten; not generated by QM.

## Building and Running

```sh
pixi run build-port-validation-rp2040
pixi run upload-port-validation-rp2040 /dev/ttyACM0
pixi run validate-rp2040 /dev/ttyACM0        # host-driven procedures, results JSON
pixi run stress-rp2040 /dev/serial/by-id/... 3600   # an hour of trace-host cycling
```

`tools/port_validation_rp2040.py` starts `qspy`, attaches to its UDP
front-end, and checks QS-RX (`Trg-Info`), counter progress, publish, dynamic
events, role switching, counter reset and, last, the assertion path including
the reboot and re-attach. `tools/port_validation_stress.py` cycles a fast or
deliberately slow trace host against the firmware and flags any cycle whose
tick counter stops advancing; it is how the shared-alarm-pool tick defect was
found. Timing measurements of tick period, tick-callback duration and
tick-to-dispatch latency need a logic analyzer on the two probes, with the LED
pin in role 1.

## The Tick Source

The BSP claims a hardware timer alarm of its own and re-arms it from its own
interrupt, catching up if a target was missed; the idle loop watches the tick
and emits a `TICK_LOST` record if it ever has to re-arm it. The trace
transport is serviced only when `QP_ARDUINO_QS_SERVICE_BYTES` are pending or
`QP_ARDUINO_QS_SERVICE_US` have passed. See `docs/port-notes.md`.
